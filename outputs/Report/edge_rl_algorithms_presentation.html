Greedy — آستانه‌ساده و مکان‌آگاه

ساده‌ترین استراتژی ممکن: فقط به «اشغال صف» و «نرخ رد شدن» نگاه می‌کند. هیچ حافظه یا یادگیری‌ای ندارد؛ هر تیک تصمیم را کاملاً مستقل از تیک قبلی می‌گیرد. نقش این الگوریتم baseline است — معیاری که VOILA و PPO باید از آن بهتر عمل کنند.

۱
scale_decision: اگر اشغال صف بیش از ۷۰٪ بود یا درخواستی رد شده بود → SCALE_UP.
۲
scale_decision: اگر اشغال زیر ۱۰٪ بود و بیش از ۱ replica آماده بود → SCALE_DOWN.
۳
provision_decision: سرور روشن جدید همیشه نزدیک‌ترین سرور خاموش به منبع اضافه‌بار انتخاب می‌شود.
۴
placement: replica جدید روی نزدیک‌ترین سرور فعال به «مرکز ثقل سرورهای فعال» (نه تقاضای واقعی) قرار می‌گیرد.

Greedy — شبه‌کد کامل و جدول پارامترها

GREEDY.scale_decision(service)
FUNCTION scale_decision(service):
    occ_ratio = avg_queue_occupancy / queue_len
    IF occ_ratio > 0.7 OR rejection_rate > 0:
        RETURN SCALE_UP
    IF occ_ratio < 0.1 AND n_ready_replicas > 1:
        RETURN SCALE_DOWN
    RETURN NO_CHANGE

// provision: روشن‌کردن سرور نزدیک به اضافه‌بار
FUNCTION provision_decision(servers):
    overloaded = servers WHERE utilization > 0.95
    starved   = سرویس‌هایی که هیچ سرور ACTIVE/BOOTING
                ظرفیت‌شان را ندارد
    IF overloaded OR starved:
        ref = نزدیک‌ترین منبع اضافه‌بار
        RETURN TURN_ON(نزدیک‌ترین سرور OFF به ref)
    IF idle_active.utilization < 0.45:
        RETURN TURN_OFF(idle_active)
    RETURN NO_CHANGE

الگوریتم ۲ از ۴

VOILA — تصمیم بر پایه‌ی تقاضای واقعی جغرافیایی

تطبیق‌یافته از مقاله‌ی VOILA. تفاوت بنیادی با Greedy: placement/migration بر اساس «مرکز ثقل واقعی تقاضا» (medoid موقعیت ۳۰ درخواست اخیر هر سرویس) تعیین می‌شود، نه صرفاً نزدیکی به سرورهای فعال. همچنین، برخلاف Greedy/HPA/PPO که فاصله‌ی جغرافیایی واقعی (oracle) می‌دانند، VOILA برای مسیریابی از یک سیستم مختصات مجازی Vivaldi استفاده می‌کند که RTT را فقط از طریق مشاهده یاد می‌گیرد.

🎯 دو نوع نقض (Vco / Vlo)

Vco (نقض ظرفیت): اشغال صف بالا یا رد درخواست.
Vlo (نقض نزدیکی): تأخیر رفت‌وبرگشت بیش از حد مجاز — سیگنال «مکانی» که Greedy اصلاً نمی‌بیند.

📍 مرکز ثقل تقاضا (demand centroid)

medoid موقعیت جغرافیایی ۳۰ درخواست اخیر هر سرویس — placement و migration به‌سمت این نقطه هدایت می‌شوند، نه مرکز سرورهای فعال.

🛰️ مختصات Vivaldi

select_replica دیگر فاصله‌ی واقعی نمی‌داند؛ فقط از RTT مشاهده‌شده‌ی تعامل‌های قبلی یک بردار مختصات مجازی می‌سازد — دقیقاً مثل مقاله‌ی اصلی.

VOILA.scale_decision(service)
FUNCTION scale_decision(service):
    occ_ratio = avg_queue_occupancy / queue_len
    cap_violation = occ_ratio > 0.68 OR rejection_rate>0
    prox_violation = NOT cap_violation AND
                      proximity_violation_rate > 0

    IF cap_violation:
        reset(good_streak, prox_streak)
        RETURN SCALE_UP                    // V_co

    IF prox_violation:
        prox_streak += 1
        IF prox_streak < PROXIMITY_SUSTAIN_TICKS:  // =2
            RETURN NO_CHANGE               // صبر برای تداوم
        prox_streak = 0
        proximity_recent = PROXIMITY_PROTECTION_TICKS  // =5
        RETURN SCALE_UP                    // V_lo

    good_streak += 1
    proximity_recent -= 1  // حداقل صفر
    IF proximity_recent > 0:
        RETURN NO_CHANGE           // محافظت موقت

    IF good_streak >= SCALE_DOWN_PATIENCE_TICKS   // =3
       AND occ_ratio < 0.20 AND ready>1:
        RETURN SCALE_DOWN
    RETURN NO_CHANGE

پارامترهای VOILA و منطق کالیبراسیون هرکدام

این جدول مهم‌ترین بخش برای داوران است: هر عدد یک دلیل مهندسی مشخص پشت خودش دارد، نه یک انتخاب دلبخواهی.

پارامترمقدارچرا این‌طور تنظیم شده
OCC_UP_THRESHOLD0.68 در بازبینی اخیر از 0.75 کاهش یافت تا VOILA زودتر از Greedy (0.70) به ازدحام واکنش نشان دهد — این حساسیت بیشتر منجر به بهبود response-time و کاهش نقض deadline شد (اما با هزینه‌ی انرژی؛ اسلاید نتایج را ببینید).
OCC_DOWN_THRESHOLD0.20 دقیقاً هم‌راستا با آستانه‌ی ممیزی مستقل سیستم (decision_audit) — یعنی تصمیم SCALE_DOWN داخلی VOILA همان چیزی است که ممیزی بیرونی هم «لازم» تشخیص می‌دهد.
SCALE_DOWN_PATIENCE_TICKS3 باید ۳ تیک متوالی (۹۰ ثانیه) سالم ببیند تا SCALE_DOWN بزند — ضد نوسان، مشابه فلسفه‌ی مقاله (safety/patience).
PROXIMITY_SUSTAIN_TICKS2 یک نقض نزدیکی تک‌تیکی می‌تواند نویز باشد؛ فقط اگر ۲ تیک پیاپی تکرار شود واکنش نشان می‌دهد.
PROXIMITY_PROTECTION_TICKS5 باگ رفع‌شده: مقدار قبلی (۳) دقیقاً برابر PATIENCE بود، یعنی محافظت هم‌زمان با برآورده‌شدن patience صفر می‌شد و عملاً هیچ محافظتی اضافه نمی‌کرد. مقدار جدید (۵) اکیداً بزرگ‌تر از ۳ است تا واقعاً بعد از یک SCALE_UP مکانی، چند تیک اضافه در برابر SCALE_DOWN زودهنگام محافظت شود.
PROXIMITY_L0_MS4.0 ms ثابت جدا از L0_MS پوشش اولیه (۲۰ms). چون حداکثر RTT ممکن در کل محدوده‌ی جغرافیایی فقط ~۱۱ms است، آستانه‌ی ۲۰ms هرگز trigger نمی‌شد و شاخه‌ی Vlo کد مرده باقی می‌ماند؛ ۴ms (میانه‌ی بازه‌ی واقعی RTT) این شاخه را واقعاً فعال کرد.
VOILA
Placement · Migration · Routing

سه رفتار مکانی VOILA که Greedy ندارد

۱ select_placement_server

به‌جای مرکز سرورهای فعال، replica جدید نزدیک demand_centroid (medoid موقعیت‌های اخیر) قرار می‌گیرد؛ بین کاندیدهای نزدیک (±۵km)، سروری با بیشترین ظرفیت آزاد انتخاب می‌شود.

۲ select_scale_down_victim

هنگام SCALE_DOWN، از بین نیمی از replicaها با کمترین بار، آن replica‌ای حذف می‌شود که دورترین فاصله را تا مرکز ثقل تقاضا دارد — یعنی ظرفیت اضافه از «حاشیه‌ی جغرافیایی» حذف می‌شود، نه از قلب تقاضا.

۳ select_replica (Vivaldi)

رتبه‌بندی replicaها بر پایه‌ی RTT تخمینی (نه واقعی) از مختصات Vivaldi؛ بعد از انتخاب نهایی، RTT واقعی به سیستم بازخورد داده می‌شود تا تخمین‌های بعدی دقیق‌تر شوند.

چرا این انحراف عمدی است: سند پروژه routing را بین هر ۴ الگوریتم مشترک و oracle تعریف کرده بود. برای وفاداری بیشتر به مقاله‌ی اصلی VOILA (که از Vivaldi/Serf استفاده می‌کند)، فقط select_replica در VOILA بازنویسی شد تا هیچ دانش پیشینی از موقعیت واقعی BTS نداشته باشد — مقایسه‌ای عمداً نامتقارن‌تر ولی صادقانه‌تر با فلسفه‌ی مقاله.

داستان یک باگ واقعی

چطور شاخه‌ی Vlo «کد مرده» بود و رفع شد

🔴 قبل از رفع

آستانه‌ی proximity از همان L0_MS پوشش اولیه (20ms) استفاده می‌کرد. اما حداکثر تأخیر رفت‌وبرگشت ممکن در کل محدوده‌ی جغرافیایی پیکربندی‌شده (قطر ~۱۸۲ کیلومتر) فقط:

max_RTT ≈ 2 × (2ms + 0.02×182) ≈ 11.3 ms

یعنی همیشه زیر ۲۰ms بود → proximity_violation_rate همیشه صفر → شاخه‌ی Vlo و ثابت‌های SUSTAIN/PROTECTION_TICKS هرگز اجرا نمی‌شدند.

🟢 بعد از رفع

یک ثابت مستقل PROXIMITY_L0_MS = 4.0ms فقط برای این متریک لحظه‌ای اضافه شد (میانه‌ی بازه‌ی واقعی ۴ تا ۱۱.۳ms):

IF 2 × delay_ms > PROXIMITY_L0_MS:
    proximity_violated += 1

حالا Vlo واقعاً فعال می‌شود و فلسفه‌ی اصلی VOILA — واکنش به نقض نزدیکی، نه فقط ظرفیت — عملاً در شبیه‌سازی قابل مشاهده است.

چرا این داستان مهم است: نشان می‌دهد که تفاوت متریک «پوشش اولیه» (threshold سخاوتمندانه‌ی L0_MS) با متریک «کیفیت لحظه‌ای سرویس‌دهی» (threshold سخت‌گیرانه‌ی PROXIMITY_L0_MS) باید از هم جدا باشند — یک عدد واحد نمی‌تواند هر دو نقش را درست بازی کند.

HPA — معادل واقعی Horizontal Pod Autoscaler

برخلاف Greedy و VOILA، HPA کاملاً location-unaware است: هیچ محاسبه‌ی فاصله‌ی جغرافیایی در تصمیمات آن وجود ندارد. این عمداً یک بازتولید وفادار از فرمول واقعی Kubernetes HPA است — نقطه‌ی مرجع برای «چه چیزی از دست می‌رود اگر مکان را نادیده بگیریم».

۱
ورودی فقط current_ready_replicas و نسبت اشغال صف است — نه فاصله، نه انرژی.
۲
placement: سروری با بیشترین ظرفیت آزاد — بدون هیچ ترتیب جغرافیایی.
۳
provisioning: میانگین utilization سرورهای فعال — سرور OFF بر اساس server_id مرتب می‌شود، نه haversine.
۴
نقش در مقایسه: نشان می‌دهد بدون آگاهی مکانی، چقدر avg_distance_km و network_delay بدتر می‌شود.

HPA — شبه‌کد کامل و جدول پارامترها

HPA.scale_decision(service)
FUNCTION scale_decision(service):
    current = max(n_ready_replicas, 1)
    util = avg_queue_occupancy / queue_len

    IF util<=0 AND rejection_rate<=0:
        desired = 1
    ELSE:
        desired = ceil(current × (util / TARGET=0.70))
    desired = max(1, desired)

    IF rejection_rate > 0:
        desired = max(desired, current + 1)

    IF desired > current: RETURN SCALE_UP
    IF desired < current AND current>1:
        RETURN SCALE_DOWN
    RETURN NO_CHANGE

فضای اکشن — MultiDiscrete
// ۱۵ بعد اول: برای هر سرویس
{0:NO_CHANGE, 1:SCALE_UP, 2:SCALE_DOWN}

// ۱۰ بعد بعدی: برای هر سرور

// اگر هم‌زمان چند سرور TURN_ON/OFF بخواهند،

// انتخاب همیشگی کمترین id)
از MaskablePPO (سب۳-contrib) استفاده می‌شود: پیش از انتخاب اکشن، گزینه‌های فیزیکی نامعتبر (مثلاً SCALE_UP وقتی هیچ سرور فعالی ظرفیت آزاد ندارد) از فضای احتمال حذف می‌شوند — نه فقط جریمه، بلکه حذف کامل.

چرا Action Masking حیاتی بود

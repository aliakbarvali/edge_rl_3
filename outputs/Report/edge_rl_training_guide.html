۱تصویر کلی پروژه

مسئله در یک جمله

یک شبکه‌ی «لبه» (Edge) داریم: ۱۰ سرور فیزیکی پخش‌شده در نقاط مختلف شهر شانگهای، و ۱۵ نوع سرویس که باید روی این سرورها اجرا شوند. درخواست‌های واقعی کاربران (از دیتاست واقعی BTS شانگهای) با نرخ متغیر در طول روز می‌رسند. سؤال اصلی: کدام سرورها روشن باشند، چند نسخه (replica) از هر سرویس کجا مستقر باشد، و هر درخواست به کدام replica برود — طوری که هم زمان پاسخ کم باشد، هم انرژی کمتر مصرف شود، هم بار بین سرورها متوازن باشد؟

این یعنی سه تصمیم هم‌زمان:

تصمیمتوضیح
Provisioningکدام سرور روشن/خاموش باشد
Auto-scalingهر سرویس چند replica داشته باشد
Placementreplica جدید روی کدام سرور مستقر شود

چرا مقایسه‌ی ۴ الگوریتم؟

  • Greedy — baseline ساده، تصمیم بر اساس آستانه‌های ثابت
  • VOILA — الگوریتم دانشگاهی واقعی (مقاله‌ی MASCOTS 2020) که مکان تقاضای واقعی را در نظر می‌گیرد
  • HPA — دقیقاً منطق Kubernetes Horizontal Pod Autoscaler، کاملاً کور به مکان
  • PPO — یاد می‌گیرد به‌جای قانون ثابت

معماری نرم‌افزاری — چرا اینطور طراحی شده

نکته‌ی کلیدی: یک اینترفیس مشترک (AlgorithmBase) داریم که هر ۴ الگوریتم پیاده‌سازی می‌کنند، و یک موتور شبیه‌سازی مشترک که هیچ‌وقت نمی‌داند دارد کدام الگوریتم را اجرا می‌کند. این یعنی وقتی یک باگ در موتور مشترک رفع می‌شود، دقیقاً و به‌طور یکسان روی هر ۴ الگوریتم اثر می‌گذارد — این برای مقایسه‌ی منصفانه حیاتی است.

داده‌ی CSV (درخواست‌های واقعی) ↓ موتور شبیه‌سازی discrete-event (simulator/engine.py) ↓ هر ۳۰ ثانیه یک بار تصمیم‌گیری (الگوریتم انتخاب‌شده: scale/provision/migration) ↓ هر درخواست که می‌رسد مسیریابی به نزدیک‌ترین replica با صف خالی ↓ ثبت متریک (response time, انرژی, ...) ↓ جدول مقایسه‌ی نهایی ۴ الگوریتم
چرا discrete-event به‌جای شبیه‌سازی زمان-گسسته (time-stepped)؟
چون رویدادها (رسیدن درخواست، پایان صف، آماده شدن replica) در لحظات نامنظم اتفاق می‌افتند. اگه زمان با گام ثابت جلو می‌رفت، یا باید گام خیلی ریز می‌گرفتیم (کند) یا دقت از دست می‌رفت. با heapq رویدادها دقیقاً به ترتیب زمان وقوعشان پردازش می‌شوند — معادل دقیق simpy (که در محیط توسعه قابل نصب نبود).
چرا PPO باید state/action/reward خاص این مسئله داشته باشد؟
چون تصمیمات (scale/provision) روی هر سرویس/سرور مستقل به‌نظر می‌آیند ولی به هم وابسته‌اند (مثلاً روشن‌کردن سرور باید قبل از SCALE_UP باشد). به همین خاطر MultiDiscrete با action masking لازم بود.

۲مدل دامنه (Server / Replica / Request)

سه موجودیت اصلی سیستم، در common/models.py.

۱. Server — سرور فیزیکی

تشبیه: یک ساختمان با ظرفیت محدود که می‌تواند چند «مستأجر» (سرویس) داخلش جا بدهد.
class ServerState(Enum):
    OFF = auto()       # خاموش، هیچ انرژی مصرف نمی‌کند
    BOOTING = auto()   # داره روشن میشه (۳۰ ثانیه طول می‌کشد)
    ACTIVE = auto()    # روشن و آماده‌ی کار
    DRAINING = auto()  # داره خاموش میشه (باید اول خالی بشه)

چهار حالت یک چرخه‌ی یک‌طرفه هستند: OFF → BOOTING → ACTIVE → DRAINING → OFF

🛠 اصلاح‌شده در دور دوم محاسبه‌ی توان لحظه‌ای — شمول رپلیکای DRAINING

متن صریح سند (بخش ۲.۴): «در طول DRAINING مصرف انرژی مثل ACTIVE محاسبه می‌شود». ولی کد قبلی فقط رپلیکای READY را می‌شمرد، یعنی سروری که همه‌ی رپلیکاهایش DRAINING بودند به‌غلط idle حساب می‌شد.

def instantaneous_utilization(self, now: float) -> float:
    """رپلیکاهای READY *و* DRAINING هر دو اگر در حال پردازش باشند شرکت می‌کنند."""
    busy_cpu = 0
    for r in self.hosted_replicas.values():
        if r.state in (ReplicaState.READY, ReplicaState.DRAINING) and not r.is_idle(now):
        if r.state == ReplicaState.READY and not r.is_idle(now):  # قبلی
            busy_cpu += self._cpu_of(r)
    return busy_cpu / self.capacity if self.capacity > 0 else 0.0

اثر روی نتایج: این فیکس متقارن روی موتور مشترک است، پس روی هر ۴ الگوریتم اعمال می‌شود. cumulative_energy_joule برای هر ۴ الگوریتم افزایش می‌یابد (چون قبلاً دوره‌ی DRAININگِ پرکار به‌غلط انرژی صفر/idle حساب می‌شد)، با شدت متفاوت بسته به الگوی drain هر الگوریتم.

۲. Replica — یک نسخه از یک سرویس، روی یک سرور

تشبیه: یک باجه‌ی تحویل با یک صف انتظار جلوش، که فقط یک نفر پشتش کار می‌کند.
def try_admit(self, arrival_time, cold_start_extra=0.0):
    occ = self.queue_occupancy(arrival_time)
    if occ >= self.queue_len:
        return None   # صف پره → رد میشه
    start = max(arrival_time, self.available_at)   # کِی نوبتش میشه
    finish = start + (self.exec_time + cold_start_extra)
    self.available_at = finish
    self.departures.append(finish)
    return {...}

این دقیقاً منطق یک صف FIFO تک‌سرور است: اگر باجه‌دار (replica) مشغول کار قبلی است، درخواست جدید باید صبر کند تا نوبتش شود.

۳. Request — یک درخواست کاربر

یک رکورد داده‌ای که سفر یک درخواست را از اول تا آخر ثبت می‌کند: arrival_time → queue_enter_time → service_start_time → service_end_time و در نهایت response_time_sec، deadline_violated و status.

چرا صف با شبیه‌سازی دقیق پیاده شده، نه فرمول تحلیلی (M/M/1)؟
چون فرمول‌های تحلیلی فرض می‌کنند ورود درخواست‌ها تصادفی با نرخ ثابت (Poisson) است. در این پروژه الگوی ورود واقعی و متغیر است (از دیتاست واقعی BTS)، و اندازه‌ی صف محدود است. پس باید هر درخواست واقعاً event-by-event شبیه‌سازی شود تا نتایج دقیق باشند.
چرا Replica یک deque برای departures نگه می‌دارد؟
برای این‌که در هر لحظه بشود فهمید صف چقدر پر است (queue_occupancy) — با پاک کردن اونایی که زمانشان گذشته. یک ترفند ساده برای شبیه‌سازی کارآمد اشغال صف بدون شمارش دستی هر لحظه.

۳چرخه‌ی کامل یک درخواست

هفت مرحله، در simulator/engine.py:_handle_arrival و algorithms/base.py:select_replica.

۱. درخواست می‌رسد (از CSV، با Lat/Long و ServiceID) ۲. لیست replicaهای READY آن سرویس پیدا می‌شود ۳. بر اساس فاصله‌ی جغرافیایی مرتب می‌شوند (نزدیک‌ترین اول) ۴. یکی‌یکی چک می‌شود: صفش خالیه؟ → انتخاب می‌شود ۵. اگه هیچ‌کدوم صف خالی نداشتن یا اصلاً replica‌ای نبود → رد می‌شود ۶. اگه پذیرفته شد → وارد صف FIFO می‌شود ۷. نوبتش که شد، پردازش می‌شود و response_time محاسبه می‌شود

انتخاب replica (مشترک بین هر ۴ الگوریتم)

def select_replica(self, request, candidate_replicas, servers, now):
    ranked = sorted(candidate_replicas,
        key=lambda r: haversine_km(request.bts_lat, request.bts_long,
                                    servers[r.server_id].lat, servers[r.server_id].long))
    for r in ranked:
        if r.queue_occupancy(now) < r.queue_len:
            return r
    return None

این تابع در AlgorithmBase مشترک است چون Routing یک تصمیم بلادرنگ برای هر درخواست است، نه یک تصمیم مدیریت منابع — بخشی که الگوریتم‌ها روش رقابت می‌کنند نیست.

فرمول response_time

response_time = (۲ × تأخیر شبکه) + زمان انتظار در صف + زمان پردازش واقعی

چرا ۲ برابر تأخیر شبکه؟ چون deadline یعنی end-to-end: درخواست باید برود سرور و جواب باید برگردد — تأخیر رفت + برگشت.

🛠 اصلاح‌شده در دور دوم ثبت موقعیت درخواست برای demand_centroid — انتقال به لحظه‌ی ورود

قبلاً موقعیت جغرافیایی فقط برای درخواست‌های موفق (COMPLETED) ثبت می‌شد. این یک حلقه‌ی بازخورد خودتقویت‌شونده ایجاد می‌کرد: منطقه‌ای با کمبود پوشش دائم رد می‌شود ← موقعیتش هرگز وارد demand_centroid نمی‌شود ← VOILA کور به همان کمبود می‌ماند ← کمبود ادامه‌دار.

چون deque(maxlen=30) از قبل یک پنجره‌ی recency-based بود، با انتقال ثبت به لحظه‌ی ورود، همه‌ی درخواست‌ها (موفق و رد شده) به‌طور طبیعی وارد همین پنجره می‌شوند — بدون نیاز به ساختار موازی جدید.

＋ رویداد جدید ENERGY_RESYNC — دقت محاسبه‌ی انرژی

هیچ رویداد صریحی برای «اتمام پردازش یک درخواست» در heap نبود. یعنی توان لحظه‌ای فقط وقتی رویداد دیگری (arrival بعدی یا DECISION_TICK) اتفاق می‌افتاد دوباره محاسبه می‌شد — تا ۳۰ ثانیه تأخیر در دقت. یک رویداد سبک اضافه شد که دقیقاً در لحظه‌ی اتمام هر درخواست موتور را «بیدار» می‌کند:

# simulator/engine.py — بعد از admit موفق:

# در step():

🛠 اصلاح‌شده در دور دوم مدت Graceful Termination — دینامیک به‌جای ثابت

مقدار قبلی (GRACEFUL_TERMINATION_DELAY_SEC=10) برای هر ۱۵ سرویس یکسان بود. برای سرویس‌های کند (مثلاً سرویس ۱۵: exec_time=120, queue_len=10) خالی‌شدن واقعی صف می‌تواند تا ۱۲۰۰ ثانیه طول بکشد — بیش از ۱۲۰ برابر مقدار ثابت قبلی.

def _start_replica_drain(self, r: Replica):
    ...
    drain_wait = max(CFG.graceful_termination_delay_sec, r.available_at - self.now)
    self._push(self.now + CFG.graceful_termination_delay_sec, ...)  # قبلی: همیشه ۱۰ ثانیه
    self._push(self.now + drain_wait, EventType.REPLICA_TERMINATED, (r.server_id, r.service_id))
⚠ فاز ۳ (Kubernetes واقعی): همین ریسک در k8s_adapter/realtime_dispatcher.py جدی‌تر است — قطع شدن پاد واقعی وسط پردازش یک درخواست HTTP یعنی از‌دست‌رفتن واقعی داده، نه فقط خطای متریک شبیه‌سازی. فیکس مشابه (انتظار پویا بر اساس اشغال واقعی صف در Redis، با سقف زمانی ایمن) اعمال شده، ولی چون این بخش هرگز روی کلاستر واقعی تست نشده، این محدودیت باید صریحاً در مستندات ذکر شود.

۴موتور شبیه‌سازی و چرخه‌ی تصمیم‌گیری

۴.۱ موتور discrete-event

به‌جای این‌که ساعت را ثانیه‌به‌ثانیه جلو ببریم، یک تقویم رویدادها داریم که مرتب‌شده بر اساس زمان است، و فقط می‌پریم به رویداد بعدی.
class EventType(Enum):
    REQUEST_ARRIVAL; DECISION_TICK; SERVER_BOOT_DONE; SERVER_DRAIN_DONE
    REPLICA_READY; REPLICA_TERMINATED
    ENERGY_RESYNC  # جدید — فاز ۳

۴.۲ چرخه‌ی تصمیم (هر DECISION_TICK)

def _handle_decision_tick(self, external_actions=None):
    snapshot = self._build_metrics_snapshot()
    self._update_sustain_tracking(snapshot)

    action = self.algorithm.provision_decision(...)   # اول: provisioning
    self._apply_provisioning(action, snapshot)

    for svc_id in CFG.active_services:                 # بعد: هر سرویس scale می‌شود یا نه
        decision = self.algorithm.scale_decision(svc_id, snapshot)
        self._apply_scale_decision(svc_id, decision, snapshot)

چرا provisioning اول؟ چون اگر سرویسی بخواهد SCALE_UP کند ولی هیچ سروری جا نداشته باشد، اول باید سرور جدید روشن شود.

۴.۴ Migration هنگام Drain (Make-Before-Break)

وقتی سروری با تنها replica یک سرویس در کل سیستم می‌خواهد خاموش شود، اول باید نسخه‌ی جدید جای دیگر ساخته شود. replica قدیمی READY می‌ماند تا replica جدید واقعاً READY شود — این جلوی یک پنجره‌ی زمانی از REJECTED_NO_REPLICA غیرواقعی را می‌گیرد.

چرا cooldown هم روی سرور هست هم روی سرویس؟
چون این‌ها دو تصمیم مستقل‌اند. یک سرویس می‌تواند SCALE_UP/DOWN بخورد بدون این‌که هیچ سروری روشن/خاموش شود (چون replica جدید روی سرور از قبل روشن جا می‌گیرد). پس باید هر کدام cooldown خودشان را داشته باشند.

۵.۱ Greedy — baseline ساده

تشبیه: مدیر ساده با دو قانون: «اگر صف بیشتر از ۷۰٪ پره، کارگر اضافه کن؛ اگر کمتر از ۱۰٪، کارگر کم کن.»

برای provisioning، heterogeneity-aware: پروفایل سرور جدید (edge_small/medium/large) با شدت اضافه‌بار تطبیق داده می‌شود.

۵.۲ VOILA — الگوریتم مکان‌آگاه

تشبیه: مدیر باهوش‌تر که می‌بیند از کجای شهر بیشترین تقاضا می‌آید و replica را آنجا مستقر می‌کند.

مفهوم کلیدی: demand_centroid — medoid موقعیت آخرین درخواست‌های هر سرویس (نه میانگین ساده، چون میانگین می‌تواند نقطه‌ای غیرواقعی وسط دریا بسازد؛ medoid همیشه یک نقطه‌ی واقعی از داده است).

دو معیار نقض (طبق Procedure 4 مقاله):

  • Vco (Capacity violation) — صف پر یا رد شده → فوری SCALE_UP
  • Vlo (Location violation) — صف خالی ولی درخواست‌ها از دور دست می‌آیند → بعد از چند تیک متوالی SCALE_UP

صبر برای scale-down (SCALE_DOWN_PATIENCE_TICKS=3) جلوی نوسان زودهنگام را می‌گیرد.

۶.۳ Action Masking

تشبیه: به‌جای این‌که بذاریم عامل حرکت غلط بزند و تنبیه شود، از همان اول فقط حرکت‌های مجاز نشانش می‌دهیم.

🛠 اصلاح‌شده در دور دوم — مهم‌ترین یافته عدم‌تطابق Mask با اجرای واقعی موتور

علامت: mask می‌گفت یک SCALE_UP «مجاز» است، ولی موتور موقع اجرای واقعی آن را با skip_reason="no_target_server" یا "only_one_replica_left" بی‌اثر می‌کرد — یعنی هم جریمه‌ی اکشن (PPO_PENALTY_PER_ACTION) بی‌جهت پرداخت می‌شد، هم سیگنال یادگیری آلوده می‌شد.

۶.۵ آموزش — BC Warm-Start + RL Fine-tune

داده‌ی train (۳ روز) ↓ Greedy demo جمع‌آوری می‌شود (state, action) ↓ BC warm-start (۲۵ epoch، cross-entropy) ↓ RL fine-tune (۳M timestep، ۸ محیط موازی، MaskablePPO) ↓ مدل ذخیره می‌شود ↓ Inference روی Data4.csv (بدون یادگیری، deterministic)

BC Warm-Start: Greedy روی داده اجرا می‌شود و هر (state, action) ثبت می‌شود، سپس شبکه‌ی سیاست PPO با یادگیری تحت‌نظارت (cross-entropy) روی این جفت‌ها آموزش می‌بیند — یک نقطه‌ی شروع معقول قبل از RL.

RL Fine-tune: ۸ محیط موازی (پنجره‌ی زمانی تصادفی از داده‌ی train)، ent_coef=0.01 برای تشویق exploration، VecNormalize(norm_reward=True) برای نرمال‌سازی خودکار reward.

ارزیابی نهایی روی Data4.csv (هرگز در آموزش دیده نشده)، inference-only، بدون یادگیری آنلاین.

۶.۶ Inference

چون scale_decision امضایش شامل now نیست ولی مدل باید یک‌بار در هر تیک پیش‌بینی کند، پیش‌بینی در provision_decision (همیشه اول صدا زده می‌شود) کش می‌شود:

def provision_decision(self, servers, metrics_snapshot, now):
    self._predict_and_cache(servers, metrics_snapshot, now)
    return self._cached_provision

def scale_decision(self, service_id, metrics_snapshot):
    return self._cached_scale.get(service_id, ScaleAction.NO_CHANGE)
چرا از MaskablePPO استفاده شده نه PPO معمولی؟
چون PPO معمولی امکان محدودکردن اکشن‌های نامعتبر را ندارد — یا باید با جریمه‌ی سنگین در reward یاد بگیرد (کند و ناپایدار)، یا با masking از همان اول جلوش گرفته شود (دقیق‌تر و سریع‌تر).
چرا BC warm-start لازم بود؟
RL خالص از صفر روی این مسئله کند همگرا می‌شود چون فضای اکشن بزرگ است (۲۵ بعد) و ابتدا عامل کاملاً تصادفی عمل می‌کند. BC یک نقطه‌ی شروع معقول (رفتار Greedy) می‌دهد که RL از آنجا بهبود بدهد.

۸نتایج نهایی و آماده‌سازی دفاع

۸.۱ چرا چند-seed مهم است

نتیجه‌ی یک اجرای PPO با یک seed کافی نیست برای ادعای علمی معتبر — RL ذاتاً نویزی است. evaluation/aggregate_seeds.py چند seed را اجرا و میانگین ± انحراف‌معیار گزارش می‌کند.

برای دفاع: اگر داور پرسید «کدام عدد درست است؟» — جواب: «هر دو، نتیجه‌ی seedهای متفاوت‌اند؛ عدد قابل‌اعتماد میانگین چند seed با بازه‌ی عدم‌قطعیت است، نه یک عدد تک.»

۸.۲ فاز ۳ (k8s_adapter) — صداقت درباره‌ی محدودیت

معماری فاز ۳ کامل طراحی و کدنویسی شده (اینترفیس مشترک، Kubernetes API واقعی، هماهنگی از طریق Redis)، ولی چون دسترسی به کلاستر فیزیکی وجود نداشت، این بخش هرگز validate نشده. حتی بعد از فیکس دور دوم (drain دینامیک)، این محدودیت باقی است.

۸.۳ ابزار تحلیلی سفارشی

analyze_decision_quality.py دو سؤال عمیق‌تر از معیار لحظه‌ای بخش ۸ می‌پرسد: آیا اکشن «غیرضروری» واقعاً نویز است یا پیش‌بینانه؟ و تحلیل flapping سرور. یافته‌ی کلیدی: نامتقارنی هزینه‌ی SCALE_UP (ارزان) در برابر SCALE_DOWN (پرریسک) — PPO این را خودش یاد گرفته.

۸.۴ چک‌لیست خط داستانی ارائه

مسئله (منابع لبه‌ی محدود + تقاضای متغیر) ↓ معماری مشترک (AlgorithmBase + موتور discrete-event) ↓ مدل دامنه (Server/Replica/Request + ماشین‌حالت‌ها) ↓ چرخه‌ی درخواست (مسیریابی + صف واقعی + response_time) ↓ چرخه‌ی تصمیم هر ۳۰ ثانیه (provision → scale → migration) ↓ ۳ الگوریتم قاعده‌محور (فلسفه‌های متفاوت) ↓ PPO (state → action masked → reward نرمال‌شده → BC+RL) ↓ سفر دیباگ (۱۶ باگ در دو دور، هرکدام با علامت→ریشه→اصلاح→اثر) ↓ نتایج (با صداقت درباره‌ی variance و محدودیت‌های باقیمانده)

سؤالات معماری و طراحی کلی

چرا اصلاً RL؟ چرا یک الگوریتم بهینه‌سازی کلاسیک (مثل ILP) کافی نبود؟
چون این یک مسئله‌ی تصمیم‌گیری ترتیبی و پویا با عدم‌قطعیت زیاد است. ILP نیاز به مدل دقیق ریاضی از کل سیستم دارد و باید برای هر تیک دوباره حل شود (سنگین). RL یک سیاست آموزش‌دیده دارد که بلادرنگ تصمیم می‌گیرد و می‌تواند الگوهای غیرخطی پیچیده را یاد بگیرد.
آیا نتایج روی داده‌ی دیگر (نه شانگهای) هم تعمیم پیدا می‌کند؟
نه به‌طور تضمینی — مدل روی الگوهای ترافیک همان شهر آموزش دیده. برای تعمیم به شهر/الگوی دیگر، حداقل fine-tuning مجدد لازم است.
هزینه‌ی محاسباتی PPO در inference چقدر است؟ برای بلادرنگ مناسب است؟
بله — آموزش سنگین فقط یک‌بار انجام می‌شود، ولی inference فقط یک forward pass شبکه‌ی کوچک (۲۵۶×۲۵۶، دو لایه) است که میلی‌ثانیه طول می‌کشد.
چرا فقط ۴ الگوریتم؟ چرا DQN امتحان نشد؟
PPO به‌خاطر پایداری بیشتر در فضای اکشن گسسته‌ی بزرگ و ترکیبی، و پشتیبانی مستقیم از action masking از طریق sb3-contrib انتخاب شد. مقایسه با DQN می‌توانست جالب باشد ولی خارج از محدوده‌ی این نسخه بود.

سؤالات درباره‌ی باگ‌ها و کیفیت کد

بزرگ‌ترین ریسک/محدودیت این پروژه چیست که خودت می‌دانی؟
چند مورد: (۱) فاز ۵ دور اول چند متغیر را هم‌زمان تغییر داد؛ (۲) k8s_adapter هیچ‌وقت روی کلاستر واقعی تست نشده؛ (۳) دو مکانیزم نسبتاً جدید (emergency-boot، capacity-starved) به‌اندازه‌ی کد قدیمی‌تر battle-tested نیستند؛ (۴) کالیبراسیون ثابت‌های انرژی بعد از فیکس دور دوم هنوز باید دوباره انجام شود.
چرا به‌جای رفع دستی هر باگ، تست خودکار ننوشتید؟
این واقعاً یکی از محدودیت‌های پروژه است. روش استفاده‌شده (تحلیل event-log بعد از هر اجرا + ابزار تشخیصی سفارشی) یک‌جور «تست integration بعد از واقعیت» بود، نه پیشگیرانه. تست‌های واحد روی سناریوهای خاص ارزش زیادی اضافه می‌کرد.
اگر یک تغییر را مجبور بودی برای نسخه‌ی بعدی اولویت بدهی، چه بود؟
نوشتن تست‌های واحد برای سناریوهای حیاتی (مثل «سرور با replica تک‌نسخه نباید بدون migration کامل drain شود»)، چون الان کشف باگ‌ها صرفاً از طریق تحلیل post-hoc لاگ‌ها بوده، نه پیشگیری خودکار.
چرا فیکس action mask را «اثبات‌شده» می‌گویی ولی درصد اثرش را نمی‌دهی؟
چون مکانیزم آسیب مستقیماً از کدِ reward function اثبات می‌شود (جریمه‌ی بی‌دلیل روی اکشن mask-passed-but-execution-failed) — این یک واقعیت کد است. ولی اندازه‌ی دقیق اثرش روی اعداد نهایی نیاز به تحلیل کمّی event log دارد که باید جداگانه انجام شود؛ بدون آن، فقط می‌شود گفت «مکانیزم آلوده‌کننده اثبات شده»، نه «فلان درصد افت از همین بوده».

سؤالات درباره‌ی متریک‌ها و انصاف مقایسه

چرا load_balance_cv را برای حالت تک‌سرور صفر گذاشتید، نه حذف؟
چون حذف کامل باعث می‌شد الگوریتمی که بیشتر وقتش تک‌سرور است (مثل Greedy) به‌طور مصنوعی این متریک را بهتر نشان دهد — دقیقاً همان تیک‌هایی که «توازن بی‌معنی» بودند از میانگین حذف می‌شدند، نه بی‌طرف حساب می‌شدند. صفر گذاشتن (نه نامتوازن، نه حذف) منصفانه‌تر است.
آیا فیکس شمول DRAINING در انرژی، رتبه‌بندی الگوریتم‌ها را عوض می‌کند؟
این یک فیکس متقارن روی موتور مشترک است، پس به‌طور یکسان روی هر ۴ الگوریتم اعمال می‌شود. مقادیر مطلق انرژی افزایش می‌یابند، ولی چون الگوریتم‌ها با فرکانس/شدت متفاوت drain می‌کنند، اثر دقیق روی رتبه‌بندی نسبی باید بعد از اجرای مجدد اندازه‌گیری شود — ادعای قطعی بدون این اندازه‌گیری درست نیست.

سؤالات درباره‌ی PPO

چرا BC warm-start لازم بود؟ RL خالص چرا کافی نبود؟
RL خالص از صفر روی فضای اکشن ۲۵بعدی کند همگرا می‌شود. BC یک نقطه‌ی شروع معقول (رفتار Greedy) می‌دهد که RL از آنجا بهبود دهد.
چرا معلم Greedy انتخاب شد نه VOILA؟
چون Greedy ساده‌ترین و قابل‌اعتمادترین baseline موجود است. هدف warm-start صرفاً دادن نقطه‌ی شروع «معقول» است، نه بهترین ممکن.
بعد از فیکس دور دوم، آیا مدل قدیمی همچنان قابل‌استفاده است؟
خیر. چون هم فضای mask (معنای معتبر/نامعتبر بودن اکشن‌ها) و هم دینامیک موتور مشترک تغییر کرده، مدل قدیمی از نظر رفتاری دیگر با محیط فعلی سازگار نیست، حتی اگر فایل بدون خطا لود شود. باید کاملاً بازآموزی شود.
